# 스킬과 플러그인 문서 작성 기준

## 1. 목적

스킬과 플러그인 문서는 에이전트와 사람이 지금 무엇을 하면 되는지 바로 알 수 있게 쓴다. 판단이 필요한 내용은 스킬에 두고, 기존 CLI 명령으로 수집할 수 있는 내용은 그 명령을 그대로 쓴다.

## 2. SKILL.md 구성 순서

1. frontmatter `name`, `description`
2. 목적 1–2문장
3. `## 절차`: 번호 목록
4. `## 결과`: 형식
5. `## 예시`: 1개 이상
6. `## 경계`: 필요할 때만
7. `## 참고 자료`: 링크

세부 규칙은 `references/`에 두고 링크한다.

## 3. description

- `<무엇을> <언제> 사용한다`를 한 문장으로 쓴다.
- 실제로 혼동되는 다른 대상이 있을 때만 구분 문장 하나를 덧붙인다.

## 4. 행동으로 정의

- 각 규칙은 `무엇을 한다` 형태로 쓴다.
- 경계 문장은 되돌리기 어려운 피해를 막는 경우에만 쓴다.
  - 원격 쓰기
  - 데이터 삭제
  - 권한 확대
  - 다른 스킬이 담당하는 작업
- 경계 문장은 `## 경계` 목록 하나에 모은다.

| 바꾸기 전 | 바꾼 뒤 |
|---|---|
| 패턴 이름을 먼저 정하는 도구가 아닙니다. | 문제와 제약을 확인한 뒤 적합한 패턴을 고릅니다. |

## 5. 현재 상태만 쓰기

현재 동작과 사용법만 쓴다. 다른 정보는 담당 위치에 둔다.

| 정보 | 위치 |
|---|---|
| 출처·라이선스·기준 commit | `UPSTREAM.md` |
| 결정 이유 | `docs/decisions/` |
| 이전 구성에서 이동하는 절차 | [`docs/guides/migrating-from-earlier-versions.md`](migrating-from-earlier-versions.md) |
| 변경 경위 | Git 기록 |

## 6. 내부 정보의 위치

카탈로그 집계, snapshot 날짜, 검증기 상수는 그 데이터를 소유한 파일이나 reference에 둔다.

플러그인 README는 다음 순서로 쓴다.

1. 한 문장 소개
2. 설치
3. 스킬 표: `스킬 | 사용할 때 | 결과`
4. 사용 예시
5. 구성: 필요할 때만
6. 검증 명령

## 7. 예시

- 대표 입력과 결과를 1개 넣는다.
- 판단이 갈리는 경계가 있으면 대조 예시를 1개 더 넣는다.
- 명령, 필드, ID는 실제 인터페이스와 일치시킨다.
- 같은 유형의 변형 사례는 `evals/`에 둔다.
- 평가 사례와 같은 시나리오는 예시로 쓰지 않는다.

## 8. 명령과 스크립트

기존 CLI(`git`, `gh` 등)로 수집하거나 판정할 수 있는 단계는 그 명령을 스킬에 쓴다. 스킬에는 다음만 쓴다.

- 실행할 명령
- 읽을 출력 필드
- 결과별 행동

스크립트는 기존 CLI로 얻을 수 없는 계산·검증이 필요하거나, 명령 조합을 손으로 따르면 결과가 실제로 달라질 때만 둔다. 근거는 [ADR 0028](../decisions/0028-prefer-cli-over-bundled-scripts.md)에 있다.

## 9. 한 규칙은 한 곳에

여러 스킬이 공유하는 규칙은 `references/`의 파일 하나에 두고 링크한다.
